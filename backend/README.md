# GameWingo Score Engine (FastAPI)

Событийный скоринг каталога: игры шлют сырые события и финальный результат,
сервер по конфигам считает баллы, звёзды, задания и достижения и применяет
антифрод. Игра не начисляет баллы никогда (железное правило каталога №1).

## Запуск

```bash
cd backend
pip install -r requirements.txt
GAMEWINGO_AUTH=demo uvicorn app.main:app --reload   # http://127.0.0.1:8000
pytest                                               # тесты движка, антифрода, JWT и API
```

`GAMEWINGO_AUTH=demo` — локальный демо-режим: пользователь берётся из заголовка
`X-User-Id` без проверки. Без него и без `GAMEWINGO_JWKS_URL` маршруты игрока
отвечают 503 (см. «Авторизация» ниже). Тот же флаг открывает админку и аналитику
без `ADMIN_TOKEN`. Пользователи, баланс и override-ы конфигов живут в памяти
процесса, пока не задан `GAMEWINGO_DB`. Админка баланса — http://127.0.0.1:8000/admin/ui,
аналитика — http://127.0.0.1:8000/analytics/ui, документация API — /docs.

Анонимный монитор пилота статического сайта запускается **отдельно**:
`uvicorn app.monitor.main:app`. Закрытый отчёт — `/monitor/ui`, данные — в
SQLite на постоянном диске. Подключение к каталогу, пароль и ограничения
описаны в [инструкции мониторинга](../docs/PILOT-MONITOR.md).

## Откуда берутся правила

Источник истины — TypeScript-конфиги `packages/game-progress/src/config`
(+ реальные лестницы уровней из `games/<slug>/src/core/levels.ts`).
Команда `npm run progression:export` в корне монорепо выгружает их в
`app/progression/configs/*.json`; сервер читает эти JSON. Админка может
переопределить конфиг без релиза (PUT /admin/configs/{game}) — override
приоритетнее файла.

## Эндпоинты

| Маршрут | Что делает |
|---|---|
| `POST /progression/events` | пакет сырых событий → баллы по конфигу игры |
| `POST /progression/result` | итог партии → баллы за завершение, звёзды по goals уровня, тарифы каталога (первое прохождение, слово дня), задания дня, достижения |
| `POST /progression/checkin` | чек-ин за вход: серия 5→10→…→25, пропуск дня сбрасывает |
| `GET /progression/games` | список игр с конфигами |
| `GET/PUT /admin/configs/{game}` | посмотреть/переопределить конфиг (с валидацией схемы) |
| `POST /admin/simulate/{game}` | прогноз начислений по профилю игрока |
| `POST /admin/configs/{game}/rollback` | откат к версии из истории |
| `GET /analytics/summary` | всё для дашборда: итоги, игры, воронка, уровни, удержание, экономика |
| `GET /analytics/ui` | страница аналитики (мобильная) — см. `docs/ANALYTICS.md` |
| `POST /analytics/demo` | заполнить демо-данными, пока нет боевого трафика |

## Деплой на Railway

В сервисе Railway: New Project → Deploy from GitHub repo → этот репозиторий,
в настройках сервиса **Root Directory = `backend`** (монорепо). Конфиг сборки
уже лежит рядом (`railway.json`): Nixpacks находит `requirements.txt`, старт —
uvicorn на `$PORT`, healthcheck — `/health`.

Переменные окружения сервиса:

| Переменная | Зачем |
|---|---|
| `ADMIN_TOKEN` | обязательно: без него админка и аналитика отвечают 503 (закрыто по умолчанию) |
| `GAMEWINGO_DB` | обязательно: путь к файлу SQLite на томе, напр. `/data/gamewingo.sqlite3`; без него маршруты игрока отвечают 503 |
| `GAMEWINGO_ORIGINS` | домены каталога через запятую (для CORS), напр. `https://gamewingo-soz.vercel.app` |
| `GAMEWINGO_JWKS_URL` | обязательно: адрес публичных ключей партнёра (JWKS), по ним проверяется JWT игрока |
| `GAMEWINGO_JWT_ISSUER` | ожидаемый `iss` токена партнёра; не задан — не проверяется |
| `GAMEWINGO_JWT_AUDIENCE` | ожидаемый `aud`, по умолчанию `wingo-games` |
| `GAMEWINGO_JWT_ALGORITHMS` | допустимые подписи через запятую, по умолчанию `RS256,ES256` |

Для `GAMEWINGO_DB` сервису нужен том: Railway → сервис → Volumes → Mount path
`/data`. Без тома файл лежит в контейнере и пропадает при редеплое.

`GAMEWINGO_AUTH=demo` на публичном сервере не задавать: он отключает проверку
JWT и открывает админку.

## Точки боевой интеграции

- **Авторизация** — JWT финтех-приложения, который игра получила в INIT и шлёт
  в `Authorization: Bearer` (`app/auth.py`). Подпись проверяется по JWKS партнёра,
  обязательны `exp` и `sub`; `sub` — обезличенный ID, которому идут баллы.
  Закрыто по умолчанию: без `GAMEWINGO_JWKS_URL` маршруты игрока отвечают 503,
  `X-User-Id` принимается только при `GAMEWINGO_AUTH=demo`.
- **Игры без экономики** — `block-drop` и `color-sort` (`UNSCORED_GAMES` в
  `config_loader.py`): партия записывается в аналитику, баллы не начисляются,
  пока у игры нет конфига прогрессии. Неизвестная игра — 404.
- **Хранилище** — SQLite на постоянном диске (`app/persistence.py`): кошельки,
  аудит, факты аналитики и override-ы админки пишутся после каждого запроса
  игрока и читаются при старте. Рассчитано на один экземпляр сервера; для
  нескольких — тот же интерфейс поверх Supabase (`migrations/001_progression.sql`,
  не применена). На постоянном хранилище `POST /analytics/demo` и
  `DELETE /analytics/data` отвечают 409: оба стирают аудит целиком.
- **Админка и аналитика** — `ADMIN_TOKEN` в окружении и в заголовке
  `X-Admin-Token`; без переменной разделы отвечают 503.
- **CORS** — домены каталога в `GAMEWINGO_ORIGINS` (через запятую).

## Идемпотентность наград

Ключи выданных наград совпадают с клиентским демо-кошельком
(`packages/game-progress/src/bonus.ts`): `level-<slug>-<n>`,
`soz-daily-<dayId>`, `quest-<id>-<dayId>`, `ach-<id>`, `checkin-<dayId>`.
Повторная отправка того же результата ничего не доначисляет, а при переезде
клиента с демо-витрины на сервер игрок увидит те же цифры.
