# Феникс: контракт серверного этапа

Статус: локальный пилот и отдельный код тестового API с подписанными токенами готовы ([инструкция](PILOT-TEST.md)); **не подключены к банковскому приложению**. Проверенной личности игрока приложения и согласованной базы для публичного запуска пока нет.

## Что нужно подключить до выпуска

1. Приложение передаёт подписанный токен игрока, сервер проверяет его и извлекает устойчивый `userId`. Заголовок `X-User-Id` сейчас демонстрационный; ему нельзя доверять для общего прогресса.
2. 16 игр с наградами отправляют структурированный `GAME_RESULT` с `game`, `sessionId`, режимом, длительностью и метриками. Прототипы `tanks` и `tap-hoops` пока не участвуют в наградах феникса. Старый `GAME_OVER` сохранён для приложения. В локальном пилоте браузерный скрипт передаёт результат в `/pet/result`; в публичной сборке такой передачи нет. Для боевого Score Engine ещё нужны конфиги `block-drop` и `color-sort`.
3. Для каждой игры задаётся правило «содержательной партии» на сервере. Успешное и проигранное завершение могут давать искру; пустой запуск и мгновенный выход — нет. Нынешняя проверка антифрода ограничивает максимум времени и счёта, но не подтверждает содержательность партии.
4. Создаётся постоянное хранилище. Среди подключённых к аккаунту проектов Supabase сейчас нет проекта GameWingo; существующую базу другого продукта использовать без отдельного решения нельзя.

## Правило начисления

Единственная точка начисления — обработка принятого результата партии на сервере. Операция должна быть атомарной: проверить повтор `sessionId`, факт искры за `(userId, dayId, gameId)` и дневной лимит 3, затем записать искру. День определяется по `Asia/Tashkent` на сервере. При одновременных результатах двух игр четвёртая искра не появляется. Повтор запроса возвращает уже записанное состояние. Искры не участвуют в денежных или бонусных расчётах.

Рекомендуемая структура: профиль питомца (`userId`, имя, настройки отображения) и неизменяемый журнал искр (`userId`, `dayId`, `gameId`, `sessionId`, время). Уникальные ограничения на `(userId, dayId, gameId)` и `(userId, sessionId)` защищают от повторов; транзакционная блокировка по игроку защищает дневной лимит. Общее число искр и стадия выводятся из журнала. Для базы, доступной через Data API, нужны включённый RLS и политики владельца; серверные секреты не попадают в WebView.

## API для клиента

Нынешний локальный пилот использует отдельные `GET /pet/state`, `POST /pet/result` и `PATCH /pet/name`. Они включаются только флагом `GAMEWINGO_PET_PILOT=1` и принимают тестовый UUID, поэтому **не подходят для публичного клиента**. Целевой контракт приложения после подключения авторизации:

- `GET /progression/pet` → `{totalSparks, todaySparks, stage, nextStageAt, name, lastSpark}`. Ответ выдаётся только проверенному игроку.
- `POST /progression/result` → нынешний результат плюс `pet: {awarded, state, reason}`. Клиент не отправляет число искр и не вызывает отдельный маршрут «начислить».
- `PATCH /progression/pet` с `{name}` → проверка длины и безопасного текста; имя доступно после вылупления. Изменение имени не влияет на искры.

Если проверка результата не пройдена или сервер недоступен, экран не показывает обещанную искру. Локальное `wingo:phoenix:demo:v1` остаётся отдельно: его число нельзя молча принять за серверный прогресс, поскольку клиент может изменить `localStorage`.

## Проверка перед включением

- Повтор одного `sessionId`, повтор одной игры за день и два параллельных результата дают не более одной искры за игру и трёх в день.
- Смена суток в Ташкенте открывает новый дневной лимит, не обнуляя общий рост.
- Два устройства одного игрока читают одинаковое состояние; два игрока не видят прогресс друг друга.
- Проигранная содержательная партия учитывается, пустая — отклоняется по правилу своей игры.
- Отказ базы или авторизации не превращается в локальное «успешно начислено».

Следующий шаг для испытания в приложении: выбрать источник проверяемого токена игрока и постоянную базу GameWingo, перенести атомарный журнал искр из локального SQLite и подключить обработку `GAME_RESULT` в нативном хосте. Локальный браузерный пилот делает эту обработку через `phoenix-pilot.js` только при явной сборке с `GAMEWINGO_PET_PILOT_API`.
